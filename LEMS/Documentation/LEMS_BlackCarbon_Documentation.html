LEMS_BlackCarbon Documentation

Black Carbon Data Entry & Optical Analysis Pipeline — Independent Flow Rates, Filter IDs, Fallback Architecture & Calculation Engine

Decoupled Black Carbon Architecture

In this branch (black-carbon-second-window), Black Carbon (BC) data entry is fully decoupled from Gravimetric (Grav) data inputs and outputs. This architecture is purpose-built for multi-line sampling configurations, specifically:

  • Three-Line LEMS (3 LPM without Flow Sensor): Physical lines pulling at a constant calibrated rate (e.g., 3.0 L/min) without a digital inline sensor. Users can manually specify this flow rate independently of the digital sensor on the gravimetric channel.
  • High-Flow Lines (16.7 LPM): In-stack or cyclone-driven high-flow sampling lines where flow rate and filter IDs do not match the standard gravimetric channel.
  • Independent Filter IDs: Allows different physical filters to be used for gravimetric PM and Black Carbon analysis during the same test phase without naming collisions or data overwrites.
Key Functional Takeaways:
  • Custom Flow Rate (Qsample_<phase>): The user can enter a custom flow rate that overrides the digital flow sensor value from GravOutputs.csv.
  • Custom Filter Number (filterID_<phase>): The user can specify a BC filter number distinct from the filter number in GravInputs.csv. The image processor searches for <testname>_<filterID>.jpeg using this BC filter ID.
  • Authoritative Storage: All user entries are saved to <testname>_BCInputs.csv, which becomes the single source of truth for downstream calculations.

1. Pipeline Architecture & Lifecycle

Decoupled Architecture

Overview Execution Flow & File Roles

The BC pipeline is implemented in LEMS/LEMS_BlackCarbon.py through the primary function LEMS_BlackCarbon(...). It can be triggered interactively via the Level 1 / Level 2 Data Entry GUI or called headlessly in automated batch scripts.

File Roles & Precedence

Status File Name Pattern Role & Precedence
Fallback <testname>_GravInputs.csv Gravimetric Inputs: Loaded early to discover active test phases and supply fallback filterID_<phase> values. Missing files trigger a warning rather than a fatal crash.
Fallback <testname>_GravOutputs.csv Gravimetric Outputs: Loaded early to supply fallback values for phase_time_<phase> and digital flow rate Qsample_<phase>.
Authoritative <testname>_BCInputs.csv Black Carbon Inputs: Pre-existing values take top priority over all Gravimetric fallbacks. Newly entered values from the interactive modal are committed directly here.
Required <testname>_<filterID>.jpeg Filter Photograph: Filter card image containing four radial QR codes, 10-step gray calibration bars, and the central deposited filter spot (fallback extensions: .jpg, .png).
Output <testname>_BCOutputs.csv Calculated Results: Contains final metrics including BCloading, BCconcentration, BCmass, and BCemissionrate.
Output <testname>_<filterID>_Debug.jpg Verification Image: Processed image overlay with circular detection bounds for user visual inspection.

2. Step-by-Step Data Entry & Fallback Rules

Implementation Details

Step 1 & 2 Early Gravimetric Loading & Existing BC Check

Before requesting user input, LEMS_BlackCarbon.py loads all available context to pre-fill the form cleanly:

  • GravInputs.csv is parsed for variable names containing filterID.
  • GravOutputs.csv is parsed for gravimetric exposure durations and digital flow rates.
  • If BCInputs.csv already exists in the test directory, its values are loaded into existing_bcval. These existing BC inputs supersede gravimetric defaults.
Fault-Tolerant Fallback Design: If GravInputs.csv or GravOutputs.csv are missing or incomplete, the script logs a warning (e.g. Warning: GravOutputs file not found) and continues. The user can still enter full BC parameters manually in the modal.

Step 3 & 4 Phase Discovery & Fallback Hierarchy

Active test phases (such as hp, mp, lp, L1, L5) are dynamically discovered from keys containing filterID_. Any phase with a blank filter entry is ignored. For each active phase, default values are assigned according to the following strict hierarchy:

Parameter Primary Source (Priority 1) Secondary Fallback (Priority 2) Default if Missing Unit
filterID_<phase> BCInputs.csv GravInputs.csv (filterID_<phase>) "" (Blank) text
phase_time_<phase> BCInputs.csv GravOutputs.csv (phase_time_<phase>) "" min
Qsample_<phase> BCInputs.csv GravOutputs.csv (Qsample_<phase>) "" l/min
filterRadius_<filter> BCInputs.csv Default standard radius 1.95 mm

Step 6 & 7 Interactive Data Entry Modal (Filter Inputs)

When running in interactive mode (inputmethod == '1'), an easygui.multenterbox dialog opens titled "Filter Inputs".

Prompts are grouped cleanly by phase, followed by filter radii:

Field Grouping in the Modal: For every discovered active phase, the dialog requests:
1. filterID_<phase>
2. phase_time_<phase>
3. Qsample_<phase>
Followed by the deposit radius for each active filter:
4. filterRadius_<filterID>

User Override Guidance

  • Specifying a Different Flow Rate:
    If the gravimetric digital flow rate in GravOutputs.csv is 0.0014 l/min, but the black carbon sample was pulled on a separate 3 LPM line, the user enters 3.0 in Qsample_<phase>.
  • Specifying a Different Filter Number:
    If the gravimetric filter was 1, but black carbon was collected on filter 201, the user changes filterID_<phase> from 1 to 201.
  • Radius Retention:
    Any inactive filter radii in pre-existing BCInputs.csv are retained on disk but omitted from the active popup to keep the dialog compact and clear.
Tip on Image Naming: The photo filename on disk must match the exact filter ID entered in this popup: <testname>_<filterID>.jpeg (or .jpg / .png). If you enter filter 201, ensure your image is named <testname>_201.jpeg.

Step 8 & 9 Re-derivation & Persistence to BCInputs.csv

Once the user clicks OK:

  • Active Filter Re-derivation: The list of filters is dynamically rebuilt from the newly edited filterID_<phase> values in bcval.
  • Auto-Radius Assignment: If the user specified a new filter number, filterRadius_<new_filter> is automatically initialized (defaulting to 1.95 mm).
  • Disk Persistence: The authoritative <testname>_BCInputs.csv file is saved using io.write_constant_outputs(...).

Step 10 Optical Image Detection & Emission Calculations

For each filter identified in filters, the pipeline executes the following optical and physical calculations:

1. Image Detection & Alignment

  • Locates image file: <testname>_<filter>.jpeg (or .jpg, .png).
  • Resizes image to canonical dimensions (ResizeImageConstants.LargestSide).
  • Detects 4 corner QR codes (detectQR) for coordinate transformation.
  • Samples 10-step radial gray calibration gradient bars (getGrayBarsRadial).
  • Identifies filter deposit circle coordinates (detectBCFilterFixed) and saves <testname>_<filter>_Debug.jpg.

2. Reflectance & Calibration Curve Matching

  • Samples RGB values within the filter radius: sampledRGB = bcFilter[0].sample(...).
  • Rates the filter against the standard BC_TOT calibration curve:
    bccResult = rateFilter(sampledRGB, bcGradient, gradient)
  • Calculates Black Carbon surface loading (bcLoading in μg/cm²).

3. Physical Emission Calculations (Decoupled)

Exposure duration and flow rate are loaded strictly from bcval (the user-entered BC inputs), completely isolated from GravOutputs.csv:

exposedTime = bcval['phase_time_' + phases[filter]]
airFlowRate = bcval['Qsample_' + phases[filter]]
bccCalcs = computeBCC(filterRadius, bcLoading, exposedTime, airFlowRate)

The resulting outputs generated per filter and phase are saved to <testname>_BCOutputs.csv:

Variable Name Units Description
BCloading_<filter>_<phase> ug/cm^2 Surface concentration of Black Carbon deposited on the filter membrane.
BCconcentration_<filter>_<phase> cm^3/ug (or ug/m^3) Volumetric concentration of Black Carbon in sampled exhaust gas.
BCmass_<filter>_<phase> ug Total mass of Black Carbon collected during the phase.
BCemissionrate_<filter>_<phase> ug/min Black Carbon emission rate based on user-specified exposure time.
